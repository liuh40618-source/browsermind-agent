# BrowserMind 三场景讲解指南

> 同一个项目，三种受众、三种讲法。本文所有数字与能力均基于当前真实代码（71 个 pytest 用例 / 7 个 @tool 注册工具 / 6 个 agent 模块），不编造未实现的指标。

---

## 0. 事实基线（三个场景共用，必须记牢）

**一句话定位**：BrowserMind 是一个自主 AI Agent——输入一句自然语言任务，它自己规划步骤 → 操控真实浏览器 → 解析网页 → 反思自检 → 生成可下载的 Markdown 报告，全程通过 WebSocket 在前端实时可视化。

**技术栈**

| 层 | 技术选型 |
|----|---------|
| Agent 编排 | 纯 Python 异步循环（think → act → observe），OpenAI function calling |
| 浏览器自动化 | Playwright（非无头可看真实操作） |
| 网页解析 | BeautifulSoup + Readability + html2text → 干净 Markdown |
| LLM | OpenAI 兼容 API（Qwen / DeepSeek / GPT / 智谱，可运行时切换） |
| 后端 | FastAPI + WebSocket |
| 前端 | React（CDN 单文件）+ WebSocket 实时三栏工作台 |
| 存储 | SQLite（任务父子关联 parent_id + 报告更新 update_report + WAL） |

**工程化硬指标**

- 71 个 pytest 用例，覆盖 11 个测试文件
- ruff（F 规则）静态检查 + mypy 类型检查
- Docker + docker-compose 一键部署（数据卷持久化）
- GitHub Actions CI（每次提交自动跑测试）
- 可选 AUTH_TOKEN 鉴权（REST 用 `X-Auth-Token`，WebSocket 用 `token` 字段，`/api/health` 与 `/` 始终放行）

**核心模块**：`agent/`（state / llm / planner / agent_loop / analyst / reflection 共 6 个）、`tools/`（browser / search / parser + 工具注册表）、`main.py`、`store.py`、`settings_store.py`、`config.py`、`frontend/index.html`。

# 场景一：毕业设计答辩

**受众**：答辩委员会老师（计算机/软件工程背景，未必做 AI 细分，但懂工程）
**核心诉求**：体现「完整工程能力 + 设计思考过程 + 理论支撑」，每个决策都能回答「为什么这么做」
**节奏**：15–20 分钟，逻辑严谨、有取舍论证、坦诚不足

## 1. 开场陈述（30 秒）

> 各位老师好，我的毕设是 BrowserMind——一个能自主规划、操控真实浏览器、读懂网页并生成结构化报告的 AI Agent。它解决的核心问题是：**用户只给一句自然语言需求，剩下的「搜什么、点哪里、读什么、怎么总结」全部由 Agent 自主完成**。下面我从选题动机、需求分析、系统设计、核心机制、难点突破、工程质量六个方面展开。

## 2. 选题动机与问题定义

**为什么做这个**：
- 传统搜索/爬虫是「被动取数」——人决定搜什么、看哪个页面、提炼什么。信息整合的瓶颈在「人的阅读与决策」。
- 大模型本身很强，但它不能「上网操作」——它只能复述训练数据里的知识，无法获取实时信息、无法与真实网页交互。
- BrowserMind 把两者结合：**让 LLM 拥有手和眼**——手是 Playwright 真实浏览器，眼是网页解析器。这样信息检索从「人驱动」变成「Agent 自主驱动」。

**问题形式化**：给定自然语言任务 $T$，输出结构化报告 $R$，中间需要自主完成 $P$（规划）、$A$（行动）、$O$（观察）、$F$（反思）四个阶段的闭环，且全程可被人介入与纠偏。

## 3. 需求分析（拆成功能性与非功能性两类）

**功能性需求**
1. 自然语言任务 → 自动拆解为可执行步骤
2. 真实浏览器操控（打开、点击、输入、滚动、截图、取文本）
3. 网页正文提取（去广告/导航/脚本噪声）
4. 联网搜索（主备多级降级）
5. 反思自检，判断是否继续或补充
6. 生成可下载 Markdown 报告
7. 多轮追问（人在回路），且追问能重新生成报告

**非功能性需求**
- 实时可视化（用户要看到 Agent 在干什么，不是干等）
- 可中断（用户随时能停）
- 多模型兼容（不绑死某一家供应商）
- 配置安全（密钥不泄露、不误提交）
- 可部署（容器化、可鉴权）

## 4. 系统设计与技术选型（重点讲「为什么」）

老师最关心的是**选型理由**，我用三张表呈现取舍论证：

### 4.1 为什么 Agent 编排「手写异步循环」而不是用 LangChain/AutoGen？

| 维度 | 手写循环 | 框架（LangChain 等） |
|------|---------|---------------------|
| 可控性 | 完全可控，每一步可插桩、可中断 | 黑盒，调试困难 |
| 学习价值 | 能真正理解 Agent 内核 | 调用现成链 |
| 依赖体积 | 零框架依赖 | 重依赖，版本漂移风险 |
| 适用场景 | 教学/毕设/需要深度定制 | 快速出活 |

**结论**：作为毕设，我要体现对 Agent 机制的掌握而非框架熟练度，所以选了手写 `think→act→observe` 循环 + OpenAI function calling。

### 4.2 为什么浏览器选 Playwright 而不是 Selenium？

- 原生异步，与 FastAPI 的 async 生态一致，不会阻塞事件循环
- 自动等待机制成熟，对 SPA（单页应用）友好
- 一套 API 跨 Chromium/Firefox/WebKit
- 截图、网络拦截、多上下文能力强

### 4.3 为什么前端用 React CDN 单文件而不是工程化 SPA？

- 毕设阶段重点在后端 Agent 能力，前端是「可视化附属」
- 单文件零构建，部署只需一个静态目录，降低评委复现门槛
- 用 WebSocket 实时驱动，交互复杂度本就不高，不需要状态管理库

> 这三处取舍体现一个原则：**在核心（Agent）上做重，在非核心（前端）上做轻**。

## 5. 核心机制详解

### 5.1 Agent 执行循环（agent_loop.py）

```
用户任务
   │
   ▼
Planner 规划 ──→ 生成步骤列表
   │
   ▼
┌─→ Think：LLM + function calling 决定「下一步调哪个工具」
│      │
│      ▼
│   Act：执行工具（browser/search/parser）
│      │
│      ▼
│   Observe：把工具结果回灌给 LLM 作为下一轮上下文
│      │
│      ▼
│   LLM 不再调用工具？ ── 否 ──→ 回到 Think
│      │ 是
│      ▼
└── Reflection：评估完成度，决定「完成 / 补充 / 暂停等人」
                     │
                     ▼
                 Analyst → Markdown 报告
```

**关键设计**：每轮都把「工具调用 + 工具结果」作为 messages 追加进对话历史，让 LLM 像人一样「边做边看边调整」，而不是一次性规划完就死板执行。

### 5.2 工具注册表（tools/__init__.py）

用 `@tool(name, backend, method)` 装饰器把每个能力注册进 `TOOL_REGISTRY` 字典，主循环用 `TOOL_REGISTRY.get(tool_name)` 分发，**替代了原来的 if/elif 长链**。

好处：
- 加新工具只需写函数 + 加装饰器，主循环零改动（**开闭原则**）
- 工具自带 `retry_async` 装饰器，指数退避重试，网络抖动自动恢复
- 注册表可被测试直接遍历，保证「声明的能力 = 真实可用」

> 这一点是工程化的体现：把「能力发现」从硬编码变成数据驱动。

### 5.3 SPA 动态渲染处理（browser.py 的 `_goto_with_render_wait`）

现代网页大量是 JS 动态渲染，`page.goto` 返回时 DOM 可能还没挂载内容。我用**四级渐进等待策略**：

1. 先等 `networkidle`（网络空闲，最理想）
2. 失败则回退 `domcontentloaded`（DOM 就绪，不卡网络）
3. 再 `wait_for_selector("#root > *")`（等根容器挂出子节点，适配 React/Vue 挂载点）
4. 最后固定时长兜底等待（`BROWSER_RENDER_WAIT_MS`）

这样既能拿到动态内容，又不会因为某个站点永不空闲而无限卡死。

### 5.4 多轮追问防短路（agent_loop.py + store.py）

追问场景有个隐蔽 bug：LLM 看到上一轮已经生成过报告，会「偷懒」直接把旧报告换个皮返回，不重新调用工具。我的解法是三件套：
- `parent_id`：每轮追问以父任务 ID 串联，历史可追溯「这是第几轮」
- `_is_followup` 标志 + `_tool_calls_this_run` 计数：本轮如果没真正调用任何工具，就判定为「短路」，拒绝直接复用旧报告
- `/api/report/regenerate` 轻量重生成接口：复用已抓取信息直接重出报告，**不重开浏览器、不重爬页面**

## 6. 关键技术难点（答辩深挖点，准备 3 个）

**难点 A：异步 Agent 的可中断性**
- 问题：Agent 循环是多步异步，用户点「停止」时正卡在某一步，如何安全收尾？
- 方案：引入 `cancel_event`，循环每次迭代开头检查；工具层用指数退避重试避免偶发失败误判为取消。
- 价值：用户随时能停，不会「点了运行就只能干等」。

**难点 B：LLM「不调工具」的判定与防短路**
- 见 5.4。这是我从真实测试中发现的 bug——LLM 会复用旧报告，属于对 Agent 行为的深入观察。

**难点 C：密钥安全与多供应商配置**
- 问题：要支持运行时切换 4 家供应商，密钥不能泄露给前端、不能误提交 git。
- 方案：`settings_store.py` 用 `provider_api_keys` 按供应商归档密钥；`_SENSITIVE_KEYS` 使前端 `/api/settings` 不回显明文；`.gitignore` 忽略 `data/` 与 `.env`，已验证 git 不跟踪敏感文件；`validate_settings` 做白名单 + 格式校验。

## 8. 创新点与不足（坦诚）

**创新点**
1. 手写 Agent 内核，每一步可插桩可中断，工程透明度高
2. 工具注册表把能力发现数据驱动化，符合开闭原则
3. SPA 四级渐进等待策略，兼顾内容完整与不卡死
4. 多轮追问防短路守卫，是从真实测试中发现的 Agent 行为缺陷并修复

**不足（坦诚，答辩反而加分）**
- 还缺自动评测数据集，无法量化「在不同任务上的稳定性」
- 单进程，未做任务队列与水平扩展
- 报告质量依赖单次 LLM 调用，未做多轮自我精修
- 前端为单文件，未做组件化拆分（明确是取舍而非疏漏）

## 3. 技术亮点深挖（STAR，准备 3 个，面试官问哪个讲哪个）

### 亮点 A：Agent 内核与可中断性（Situation–Task–Action–Result）

- **S**：要做一个能自主完成多步网页任务的 Agent，且用户要能随时停。
- **T**：设计一个可控、可调试、可中断的执行循环。
- **A**：手写 `think→act→observe` 循环，每轮把 function call 和工具结果作为 messages 追加进上下文；引入 `cancel_event`，循环每次迭代检查；工具层用 `retry_async` 指数退避，避免偶发网络失败被误判为取消。
- **R**：Agent 行为完全透明可调试，用户随时可停，不会卡死。
- **能扛的追问**：「为什么不直接用 LangChain 的 AgentExecutor？」→ 可控性/调试/依赖体积，且我想真正理解内核而非调框架。

### 亮点 B：工具注册表与开闭原则

- **S/T**：最初工具分发是 if/elif 长链，加一个工具要改主循环，违反开闭原则。
- **A**：写 `@tool(name, backend, method)` 装饰器，函数定义即注册，进 `TOOL_REGISTRY` 字典；主循环改成 `TOOL_REGISTRY.get(tool_name)` 分发；注册表可被测试遍历，保证「声明 = 可用」。
- **R**：新增工具只写函数+加装饰器，主循环零改动；测试能自动发现所有工具。
- **能扛的追问**：「method 参数干嘛的？」→ 允许一个 Python 函数对应多个工具别名（如 `open` → `open_page`），兼容 LLM 偶发调用别名。

### 亮点 C：多轮追问防短路（最能体现对 LLM 行为的深入观察）

- **S**：多轮追问时，LLM 看到已有报告，会直接换皮返回旧报告，不重新调用工具——用户追问等于没用。
- **T**：让追问真正重新工作。
- **A**：`parent_id` 串联父子轮次；`_is_followup` + `_tool_calls_this_run` 计数，本轮零工具调用即判定短路、拒绝复用；新增 `/api/report/regenerate` 复用已抓信息轻量重出，不重爬。
- **R**：追问能真实重新生成；轻量重生成省去重复开浏览器成本。
- **能扛的追问**：「怎么判定 LLM 偷懒？」→ 看本轮 function call 次数，为零即短路。

# 场景三：路演 / Vibe Coding 黑客松展示

**受众**：评委 + 现场观众（半技术或非技术，要被「点燃」）
**核心诉求**：感染力 + 现场 demo + 故事化 + 差异化，节奏快、不堆术语
**节奏**：总时长 5–8 分钟，Hook 30 秒、Demo 3 分钟、亮点 2 分钟、收尾 1 分钟

## 1. Hook（开场 30 秒，抓人）

> （打开投影，BrowserMind 界面已就绪）
> 「我问大家一个问题：你想对比两款 AI 模型的能力，你会怎么做？打开十个标签页，搜、读、复制、粘贴、整理……半小时后你还在切窗口。」
> 「如果，我只说一句话，剩下的——搜什么、点哪里、读什么、怎么总结成报告——全部由一个 AI 自己完成呢？」
> 「这就是 BrowserMind。它不是一个聊天机器人——聊天机器人只会复述它训练时背过的东西。BrowserMind 有手有眼：手是真实浏览器，眼是网页解析器。它真的会上网，真的会点按钮，真的会读完一整页再总结。」

## 2. 现场 Demo 脚本（3 分钟，最关键）

**选一个有视觉冲击力的任务**（建议二选一）：

- **任务 A（对比类）**：「对比 GPT-4o 与 Claude 在 Agent 任务上的能力，给出结论与证据来源」
- **任务 B（实时类）**：「查今天有什么 AI 新闻，给我一份摘要带来源链接」

**演示动作流程**：
1. 在输入框打任务 → 点「点亮星图」
2. 镜头给到**认知星图**——五个阶段（规划/执行/解析/反思/报告）随执行实时连线亮起，这是视觉记忆点
3. 看 Agent 自己调用 `search` → `open_page` → `get_text`，时间线滚动
4. 如果开**非无头模式**（`BROWSER_HEADLESS=false`），让评委看到真实浏览器窗口被自动操作——「它真的在上网」
5. 右栏报告生成完毕，点下载拿到 Markdown
6. **高光时刻**：当场追问一句「再深入讲讲 Claude 的工具调用」，展示多轮追问能重新生成报告（不是换皮）

**演示话术**：
- 「看，它自己决定先搜谁、先读哪页——我没有写死任何流程，是模型自己规划的。」
- 「这一步它点开了真实浏览器——不是模拟，是 Playwright 操控的真 Chromium。」
- 「追问时它重新调用了工具，不是把旧报告复制一遍——这点我专门做了防短路。」

## 3. 技术亮点（用比喻，不堆术语，2 分钟）

- **Agent 内核**：「它的大脑是一个 think-act-observe 循环——想一想下一步干嘛、做、看结果、再想。和人干活一模一样。而且我手写这个循环，没用现成框架，所以它每一步我都看得见、能随时叫停。」
- **工具注册表**：「它会的每件事——开网页、点击、搜索、解析——都像插件一样注册在一个表里。以后想让它学会发邮件，写个函数挂上去就行，不用动它的大脑。」
- **SPA 渲染等待**：「现在很多网页内容是 JavaScript 现场画的，你打开页面那一瞬间是空的。我写了四级等待：等网络安静、等 DOM 就绪、等根节点冒出来、再兜底等一会儿——保证它读到的不是空壳。」
- **多轮防短路**：「AI 有个坏毛病——你追问时它会偷懒把上次的答案换个说法糊弄你。我加了守卫：这轮如果它没真去查，就判定它偷懒，逼它重做。」

## 4. 差异化叙事（为什么不是「又一个套壳 ChatGPT」）

> 「市面上很多 AI 应用其实是『套壳』——把大模型的 API 包一层界面。BrowserMind 不是。区别在于：套壳 AI 只能复述训练数据里的旧知识；BrowserMind 能实时上网、操控真实浏览器、读取它从没见过的页面，再总结。**它的报告引用的是真实来源链接，不是模型凭记忆编的。**」
>
> 「而且它是工程级作品——71 个自动化测试、Docker 一键部署、CI 自动跑测试、密钥安全防护。这不是 demo 玩具，是可以交付的产品底座。」

## 5. 收尾（1 分钟，愿景 + 落点）

> 「BrowserMind 让我把一件最耗时间的事——上网查资料整理成报告——交给了一个真正会上网的 AI。它的下一步是接入评测数据集量化稳定性、加任务队列支持多人并发。但今天，它已经能从一句话，走到一份带来源的报告。」
> 「谢谢，欢迎提问。」

## 附：三场景话术差异速查

| 维度 | 毕设答辩 | 简历/面试 | 路演/黑客松 |
|------|---------|----------|-----------|
| 受众 | 答辩老师 | 技术面试官 | 评委/观众 |
| 核心诉求 | 工程完整 + 设计思考 | 技术深度 + 量化 | 感染力 + demo |
| 语言风格 | 严谨、有理论 | 简洁、可深挖 | 故事化、比喻 |
| 重点 | 选型理由 + 不足坦诚 | STAR 难点 + 数字 | 现场 demo + 差异化 |
| 禁忌 | 编造未实现功能 | 堆虚词、说不清 | 念 PPT、不放 demo |
| 时长 | 15–20 min | 30 秒 + 按需 | 5–8 min |

> **一句话原则贯穿三场景**：所有数字与能力都基于真实代码，没有的就是没有——被问到没做的，坦诚说「这是 roadmap」比硬编更得分。
